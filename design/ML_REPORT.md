# On-device SMS classifier — ML report

**Status: gates met.** The bundled model and the local review learner are pure
Kotlin, work in airplane mode, and never extract or emit an amount. Model
artifacts are reproducible with `node tools/train_classifier.mjs` (seed
`20261119`, SHA-256 prefix `20be1f8bb73e`).

| Gate | Required | Achieved |
|---|---|---|
| Holdout txn precision | ≥ 0.99 | **0.995** |
| Holdout txn recall | ≥ 0.90 | **0.990** |
| Adversarial txn precision | ≥ 0.95 | **0.978** |

"Txn" means `DEBIT` or `CREDIT`; all other messages are `NOT_TXN`.

---

## 1. What the classifier does — and does not do

The classifier answers one question: **is this SMS a completed bank
transaction, and if so, is it a debit or a credit?**

```kotlin
enum class SmsClass { NOT_TXN, DEBIT, CREDIT }
data class MlPrediction(pNotTxn, pDebit, pCredit)
```

It deliberately does **not** parse amounts, account tails, references or dates.
Those remain the job of the deterministic parser in `sms-parsing-playbook.md`
§4. The classifier only narrows the pipeline's decision space; the parser's
confidence score and the Review queue remain the authority for what gets
recorded. A high ML score can never substitute for a parsed amount or bypass
the sender/confidence rules.

## 2. Features (trainer and Kotlin are byte-compatible)

Normalization:

1. lowercase,
2. trim,
3. collapse every whitespace run (`\s+`) to one space.

Features:

- Every character n-gram with **n = 2..4** over the normalized UTF-16 code
  units, including spaces, punctuation and digits.
- One binary feature per distinct n-gram: presence = `1.0f`, no counts, no bias
  feature (biases are separate model parameters).
- Hash: 32-bit **FNV-1a** over the n-gram's code units
  (`h = 2166136261; h ^= c; h = (h * 16777619) mod 2^32`), then
  **bucket = h % 1024**.
- `TextFeatures.buckets()` returns sorted unique bucket ids.

The trainer exports five `text -> buckets` vectors in
`tools/eval_report.json` (`feature_fixture`), hardcoded into
`ClassifierTest.textFeaturesMatchesTrainerFixture`. Regenerating the model
without updating that fixture must fail the JVM test, which protects against
silent trainer/runtime drift.

## 3. Model and training

- **Model:** 3-class multinomial softmax regression, weight matrix `3 × 1024`
  plus 3 biases, compiled into `ml/BundledModel.kt`. No TFLite, no downloads.
- **Optimizer:** Adam, lr `0.05`, β1 `0.9`, β2 `0.999`, ε `1e-8`.
- **Regularization:** L2 `1e-5` on weights (not biases).
- **Schedule:** batch 32, 60 epochs, deterministic seeded shuffle
  (mulberry32).
- **Loss:** softmax cross-entropy.
- **Reproducibility:** fixed seed `20261119`; no timestamps are written into
  artifacts.

### Training data (100% synthetic — no user data)

The corpus is generated by `tools/train_classifier.mjs` from randomized
templates across India, the UK and the US:

- **DEBIT:** card purchases, UPI paid, ATM withdrawals, NEFT/IMPS debits,
  autopay, subscriptions, EMI, wallet spend, international spend.
- **CREDIT:** salary, NEFT/IMPS credit, refunds, cashback, interest, wallet
  top-ups, incoming UPI.
- **NOT_TXN:** OTPs (including OTPs that mention amounts), promos/loan offers
  (including offers that mention amounts), balance-only messages, service
  messages (card blocked, statement ready, KYC), future/conditional payment
  notices ("will be debited", "is scheduled"), personal/delivery messages, and
  spam.

Amounts vary in format (`1,234.50`, `1234.5`, `₹1,23,456.00`, `£12.40`,
`$45.20`, `1.234,50`). Senders, dates, references, merchants and account tails
are randomized. Senders are recorded only for corpus inspection — the model
only ever sees the body, matching the runtime API.

| Split | NOT_TXN | DEBIT | CREDIT | Total |
|---|---:|---:|---:|---:|
| Train (generated) | 220 | 195 | 155 | 570 |
| Train (curated balance-only hard negatives) | 16 | 0 | 0 | 16 |
| **Train total** | **236** | **195** | **155** | **586** |
| Holdout (independent seed) | 100 | 110 | 90 | 300 |
| Adversarial (hand-authored, unseen) | 45 | 25 | 19 | 89 |

The 16 curated balance-only rows exist because short, digit-dense balance
alerts were the hardest negative class for a 1024-bucket model. They are
ordinary bank phrasings, not copies of the evaluation sets.

## 5. On-device learning rules

`HybridClassifier` combines two heads:

1. **BundledClassifier** — immutable weights compiled into the APK.
2. **LocalLearner** — a copy of those weights, fine-tuned on the device.

`LocalLearner.learn(body, label, lr = 0.05f)` performs exactly one SGD step on
the softmax cross-entropy, touching only the buckets present in the message.
The bundled weights are never mutated.

### When learned labels apply

- Only explicit **Review** actions call `learn`:
  - **Confirm** → `DEBIT` or `CREDIT` (the direction the user confirmed).
  - **Discard** → `NOT_TXN`.
- A learned update affects **subsequent classifications on that device only**.
  There is no upload, no telemetry, no network.
- Persistence: after each learn call the fine-tuned weights are serialized as
  JSON text to a private file in `context.filesDir` and reloaded on the next
  construction. If the file is missing or corrupt, the app falls back to the
  bundled model. Passing `context = null` keeps learning in memory only
  (used by JVM tests).
- **Merge rule:** if the bundled and local heads agree on the label, the local
  distribution is used. If they disagree, the two distributions are averaged
  (deterministic, symmetric — neither head can unilaterally flip a label).
- Clearing app data resets local learning to the bundled baseline.

The parser's confidence gate, sender whitelist and Review queue are unchanged
by the ML layer. Local learning is a convenience for recurring review
corrections, not an auto-record mechanism.

## 6. Known limitations

1. **Synthetic domain gap.** The corpus is realistic but templated. Unseen bank
   formats, unusual abbreviations, and new marketing language will not always
   generalize. Anything below the parser's confidence threshold must go to the
   Review queue; this classifier is not a licence to auto-record.
2. **1024-bucket collisions.** The contract fixes 1024 buckets and character
   n-grams. Hash collisions occasionally flip DEBIT/CREDIT on short messages;
   holdout direction accuracy is 97.98%, not 100%. The deterministic direction
   keywords and the Review queue remain the final check.
3. **Personal messages using bank verbs.** Phrases like "I received ₹1,000 from
   my cousin" can look like a credit. This is the one adversarial false
   positive. The upstream junk/personal filter should catch most of these.
4. **Future/conditional payments.** "Will be debited", "is scheduled", "is
   due" messages are explicitly represented as `NOT_TXN`, but one holdout
   future notice still scored as a transaction. Never auto-record solely on an
   ML score.
5. **English/Hinglish only.** Some Hinglish templates are included; other
   languages are out of distribution. The v2 Hindi/Hinglish keyword pack is the
   extension point.
6. **No sender signal.** The model sees the body only, consistent with the API.
   Sender whitelisting is handled separately by the SMS pipeline.
7. **Not a fraud or OTP detector.** OTP/promo coverage is strong in evaluation,
   but the ML layer is not a security control.

In every failure mode the safe outcome is the same: the candidate is shown in
the Review queue and never silently written to the ledger. The classifier never
throws away the raw SMS (audit trail first) and never supplies an amount.

## Real-world corpus + JVM eval (v0.9.4)

Two gaps closed so the bundled model can be retrained on real device data:

1. **Corpus export (on device, debug builds only).**
   `adb shell am broadcast -a app.pocketledger.DEBUG_EXPORT_CORPUS` dumps the
   `sms` table to `files/corpus/corpus-<ts>.jsonl` via `CorpusExporter`.
   Pull with `adb exec-out run-as app.pocketledger cat files/corpus/<name> > corpus.jsonl`.
   Label policy: `user_confirmed`/`user_discarded` rows are hard human labels;
   cleanly parsed rows carry a silver `ideal_label`; everything else unlabeled.

2. **JVM-side eval runner.** `MlEvalTest` scores the compiled `BundledModel`
   against the trainer's fixtures copied to `app/src/test/resources/`
   (`eval_holdout.jsonl`, `eval_adversarial.jsonl`) and enforces the same
   gates in CI: holdout txn P ≥ 0.99 / R ≥ 0.90, adversarial P ≥ 0.95.
   Metrics mirror the trainer byte-for-byte (confusion[actual][pred],
   trainer's argmax tie rule).
